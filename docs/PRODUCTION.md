# Production plan (prepared, **not executed**)

Nothing in this document has been run. No production database, Worker, secret, DNS record or merge exists yet. Every step that creates or changes something live needs the owner's explicit approval, marked **◆ owner**.

## 1. Chosen architecture
**Cloudflare Worker + static assets + a separate, fresh production D1 database.** The Worker serves `site/` and `/api/*` from one origin. The legacy website (GitHub Pages) stays up until cutover.

| Thing | Name / value |
|---|---|
| Worker | `ii-pioneer-registry` (`[env.production]` in `worker/wrangler.toml`; the file has no default environment, so a deploy without `--env` cannot overwrite it) |
| Database | `ii-pioneer-registry-production` — new, empty; never the staging database; no legacy data imported |
| Sender | `Influencers Involved <verification@influencersinvolved.org>` (Resend domain already verified [owner-reported]) |
| Secrets (Cloudflare) | `TOKEN_SECRET` (random, generated by the workflow, never shown), `EMAIL_API_KEY` (a production Resend key) |
| Cleanup | daily cron `17 3 * * *` UTC → deletes expired temporary records ([RETENTION.md](RETENTION.md)) |
| Logs | Workers Logs on, automatic invocation logs off |
| Deploy | `.github/workflows/production.yml`: manual, typed confirmation, `main` only, GitHub Environment `production` with required reviewer |
| Fail-closed | the API answers 503 `not_configured` (and `/api/health` reports `secrets_configured:false`) if `TOKEN_SECRET` is missing or shorter than 32 characters; there is no built-in fallback |

## 4. Stage 1 — dark launch (no DNS, no live-site change) **◆ owner**
After the merge to `main`: Actions → *Deploy production (manual, owner-approved)* → Run workflow on `main`; type `DEPLOY PRODUCTION`; tick **Create the production database** (first run only); keep *smoke test* ticked; approve the environment gate.
What it does: tests + dry run; builds with `PRELAUNCH=1` (noindex, `X-Robots-Tag`, `robots.txt` disallow, no staging banner); creates the database; records the D1 restore point in the run summary; applies migrations; deploys the Worker to its own `*.workers.dev` address; sets `TOKEN_SECRET` and `EMAIL_API_KEY`; smoke-tests (synthetic `smoke+…@example.invalid` registrations, flagged as tests and never counted, no email attempted) and deletes them.
You then test the printed URL: pages, form, one real registration with your own `+test` address, verification email arrives from `verification@influencersinvolved.org`, click "Confirm my email", certificate, unsubscribe. Delete your test rows with `scripts/erase-pioneer.mjs <address> --env production --confirm`.

## 5. Stage 2 — prepare the Cloudflare zone (no outage, nothing user-visible changes) **◆ owner**
Cloudflare custom domains require the DNS zone to be **active on Cloudflare** (nameservers pointing at Cloudflare). DNS is currently at Squarespace. Therefore the zone must first exist at Cloudflare, with *every* record copied, **before** nameservers move.
1. In Squarespace's domain DNS panel, **screenshot/export every record** (this is also your rollback record). Note whether DNSSEC is on (it must be switched off before changing nameservers, and the registrar's DS record removed).
2. Cloudflare → Add a domain → `influencersinvolved.org` → Free plan. Cloudflare imports what it can find, which is **not guaranteed complete** (it cannot see unknown DKIM selectors). Add/verify by hand: all Google Workspace records (MX ×5, SPF TXT, `google._domainkey` DKIM TXT, any `_dmarc`), Resend's `resend._domainkey` TXT, `send` and `rsend` CNAMEs (and any MX/TXT Resend lists under `send`), the GitHub Pages records (4 × A and, if present, 4 × AAAA at the apex; `www` CNAME to `lasallekey.github.io`), CAA and any site-verification TXT records. Set the legacy website records (A/AAAA/`www`) to **DNS only (grey cloud)** so traffic still goes straight to GitHub Pages. Squarespace may have "preset" records for Google Workspace that disappear when its nameservers are no longer used, which is why they must be recreated by hand.
3. Run the read-only comparison (GitHub repository variable `CLOUDFLARE_NAMESERVERS` = the two nameservers Cloudflare shows, comma-separated; it runs in the *Deploy staging* workflow; or ask me to run it): `scripts/dns-preflight.mjs` queries both the current DNS and the new Cloudflare nameservers for 17 watched record sets and prints `OK` only if they are identical. **Do not change nameservers until it prints OK.**
4. Lower TTLs of the existing records to 300 s a day ahead (at Squarespace, if its panel allows).
5. ◆ **Owner approves**, then at Squarespace switch the domain to Cloudflare's two nameservers. Cloudflare's zone turns *Active*, usually within minutes to hours. Re-run the comparison; check Gmail still receives mail (send to and from grants@), and that the legacy site still loads.
Rollback at any time in Stage 2: set Squarespace back to its own nameservers (the old records are untouched there).

## 6. Stage 3 — cutover (the website goes live on the new platform) **◆ owner approval required for each part**
Prerequisites: Stage 1 tested, Stage 2 zone Active and verified, Privacy page approved, Zeffy and social links checked, baseline export taken.
1. Prepare (I do this on a branch; you review) the **cutover commit**: in `worker/wrangler.toml` `[env.production]` set `workers_dev = false`, `[env.production.vars] SITE_URL = "https://influencersinvolved.org"`, and add
   ```toml
   [[env.production.routes]]
   pattern = "influencersinvolved.org"
   custom_domain = true

   [[env.production.routes]]
   pattern = "www.influencersinvolved.org"
   custom_domain = true
   ```
2. In Cloudflare DNS delete the grey-cloud legacy apex A/AAAA and `www` CNAME (Cloudflare will not attach a custom domain over existing records). **The legacy site goes dark from this moment**, so do steps 2-4 together, in a quiet hour.
3. Merge the cutover commit, run the production workflow with **cutover_complete** ticked (indexable build, SITE_URL check, smoke test against `https://influencersinvolved.org`).
4. Add a Cloudflare *Redirect Rule* `www.influencersinvolved.org → https://influencersinvolved.org` (free). Cloudflare issues the certificate automatically (minutes).
5. Verify: the seven pages, form submit, verification email → "Confirm my email", Zeffy button, footer socials, `/robots.txt` and sitemap, `view-source` shows no noindex. Mail still flows (Google) and Resend still verified.
6. Afterwards: GitHub → Settings → Pages → remove the custom domain and, once stable, unpublish Pages. Leave the legacy files in the repo (deleting them needs separate approval).
7. Submit the sitemap in Google Search Console if you use it. Keep HSTS at its default 30 days for the first month.

## 7. Rollback
| Situation | Action | Data impact |
|---|---|---|
| Bad site/API release | `npx wrangler rollback --env production --config worker/wrangler.toml` (or re-run the workflow from a previous commit) | none |
| Cutover goes wrong | In Cloudflare delete the two custom domains, recreate the legacy GitHub Pages A/AAAA/`www` records exactly as in your Squarespace export (GitHub Pages standard: A `185.199.108.153`, `.109.153`, `.110.153`, `.111.153`; AAAA `2606:50c0:8000::153` to `8003::153`; `www` CNAME `lasallekey.github.io`; DNS-only). Legacy site returns within the TTL. | New registrations stay in D1 |
| Nameserver move goes wrong | Switch Squarespace back to its own nameservers | none |
| Bad data change | D1 Time Travel restore to the bookmark in the deployment summary: `npx wrangler d1 time-travel restore ii-pioneer-registry-production --bookmark <id>` | rewinds to that moment |
| Total loss | Restore the last private export into a fresh database (below) and point the production env at it | up to the last export |
Mail is never part of this rollback: Google Workspace and Resend records are copied unchanged and verified by `dns-preflight` before and after.

## 8. Backups
- **Automatic:** D1 Time Travel [Assumption: 7 days on Free, 30 on Paid; confirm in the D1 dashboard].
- **Manual baseline (before cutover) and monthly:** `npx wrangler d1 export ii-pioneer-registry-production --remote --env production --config worker/wrangler.toml --output ii-registry-YYYY-MM-DD.sql`, stored in the organization's private storage. **Never commit it, attach it to an issue/PR, or keep it as a GitHub Actions artifact (public repositories expose artifacts); it contains private email addresses.** The export file is subject to the same erasure requests: delete old exports on a schedule you can state.
- **Restore rehearsal:** import the export into a scratch database (`wrangler d1 create ii-restore-test`, `wrangler d1 execute ii-restore-test --remote --file <export>`), compare row counts, delete the scratch database. Do this once before launch.

## 9. Observability and monitoring
Workers Logs are on (retention per plan); only our redacted `console` lines are written (errors, provider rejections, daily cleanup counts). To watch live: `npx wrangler tail --env production`. Weekly: Resend dashboard (bounces, complaints), Cloudflare Workers → Metrics (errors), D1 → Metrics. `/api/health` returns 503 when secrets are missing; an external uptime check on it is optional and would be a separate service decision.
